## Authoring rules

1. Every crisis has **ground truth** (day by day, and it can change mid-crisis), an **adversary plan** (what they want you to believe, through which channels) and a **report stream**.
2. Every planted item has **at least one tell in its own text and at least one cross-check**, an item available by that day that contradicts it. Deception must be beatable, not random.
3. Each day's inbox mixes true signals, noise, planted items and background clutter that has nothing to do with the crisis. Target: 4 to 6 items a day.
4. At least one day per crisis has to have a **diagnostic** item, one that splits the hypotheses apart. In Phase 1 it arrives in the normal inbox. From Phase 2, at least one must come from collection.
5. The **postmortem** has to be able to explain every item: what it really was and what it should have told you. For planted items it states the tell, the cross-check by item ID and the adversary's motive.
6. Fictional countries in real regions, and fictional actors only. Real terrain and generic, publicly known methods are fine. Never use real people.
7. Don't tell the player how many days a crisis lasts; in-world deadlines are fine. The **morning read-in** states only public events and the player's own posture, never hidden truth. The **map** plots reporting (planted items included), never truth, until the postmortem.

8. **Push the public, pull the secret (#51, new crises from Crisis 02).** Public channels and anything a source volunteers arrive every day (about 2–3 items). IMINT, SIGINT and HUMINT reporting arrives only through tasking.
9. **Counterintelligence deception goes where the adversary could really do it** (#51): staged traffic on a net it knows is covered, a dangle or double agent passing chickenfeed, decoys for imagery, watching for who asks. Every pulled plant still needs a tell and a cross-check reachable through push or another tasking available by that day. The diagnostic must be reachable by at least two tasking paths, and the postmortem says how the adversary knew we were looking.

## Data format (v1.0)

Each crisis is one JSON file, listed in `crises/index.json` (`id`, `file`, `number`, `title`, `line`, optional `note`), which drives the scenario list and the unlock order (#54): each scenario unlocks when the one before it in this file has been finished. The working examples are `crises/border-buildup.json` and `crises/walk-in.json`; the second is generated by `tools/build_walk_in.py`. This is the field reference.

| Field | What it holds |
| --- | --- |
| `id`, `title`, `crisisNumber`, `days`, `dayLabels` | Identity and calendar (`dayLabels` like "the 15th") |
| `briefing` | `dateLine` and `situation` paragraphs for the opening screen |
| `placeholderNote` | One line on the fictional setting |
| `customer` | `name`, `role`, `callsign`, `wants`, `context` |
| `asset` | The force the customer can move: `name` and `levels` (e.g. `home`, `company`, `battalion`, each with a `label` and `rank`) |
| `customerPolicy` | Ordered rules: `if` (`hypothesis`, `confidence`, `assetAt`) → `action` (`deploy` with a `level`, `readiness`, `hold`, `relax`, `withdraw`). `confidence` is the level the player chose: `low`, `medium` or `high`. |
| `policySummary`, `policyNote` | The customer's habits as shown to the player |
| `replies`, `replyLabels` | The customer's reply text for each outcome, and a short label for each |
| `events` | Start-of-day triggers (e.g. the early-move freeze): `atStartOfDay`, `if`, `effect`, `replyId`, `note` |
| `hypotheses` | `id`, `short`, `text`, and `claim` (the clause used in the key-judgment line, e.g. "IRON HARVEST is cover for an operation to seize Tarsk Dam") |
| `groundTruth` | Per day: `trueHypothesis`, `bestCall`, `state`, and `units` (positions shown only on the postmortem map) |
| `adversaryPlan` | Phases: `days`, `wantsYouToBelieve`, `summary`, `channels` |
| `sources` | `id`, `codeName`, `discipline`, `access`, `startingGrade`, hidden `trueReliability`, `controlledByAdversary`, `rosterHidden`, `postmortemNote` |
| `reports` | `id`, `day`, `sourceId`, `discipline`, `sourceGrade`, `credibility`, `text`, `kind` (`true`, `noise`, `planted`, `clutter`), `supports`, `contradicts`, `tells`, `diagnostic`, `pin` (map position and label), `postmortemNote`, and for planted items `reveal` (`tell`, `crossCheck.ids`, `crossCheck.text`, `motive`) |
| `tellLabels` | Human-readable label for each tell tag |
| `scoring` | `call` (right/wrong points per confidence level), `evidence` and `challenge` (points per kind), `maxEvidence`. |
| `endings` | Ordered: `if` (`assetAt`, `since`), `title`, `tone`, `points`, `text`; one has `default: true` |
| `countdown`, `dailyUpdates` | The read-in's countdown target and each day's public update |
| `map` | Illustrated map: `viewBox`, `river`, `reservoir`, `border`, `forests`, `training`, `highlands`, `regions`, `places`, `offmap`, `friendly` positions, `legend` |
| `postmortem` | `script` (per day or group of days) and `lessons` |
| `pirs` | Priority intelligence requirements shown on the Collect tab: `id`, `question`, `targets` |
| `targets` | `id`, `name`, `pin` (map position), `disciplines` that can be tasked against it |
| `collection` | `budget` per day, `costs` per discipline, `delays` (e.g. HUMINT 2 days), `sources` (which source answers each discipline), `fallback` text, `burnRules` (source, discipline, `consecutiveDays`, text, postmortem note), `burnPoints` |
| `collectionResults` | `id`, `discipline`, `target`, `from`, `to` (the tasking days that produce it). The result is the report with the same `id`, marked `via: "collection"` and left out of the base stream. Tasked again after it's been collected, or outside its window, the tasking returns the fallback. |
| `postmortem.missedCollection` | Per day: the tasking that would have mattered most |
| `credibility` | Optional. `start`, `min`, `max`; `levels` (`id`, `label`, `min`, `text`, optional `budgetDelta` and `caution`, the number of steps the customer discounts your confidence); `triggers` (`on`: `event` with `eventId`, `reply` with a reply id, or `streak` with `confidence` and `days`; plus `delta`, `rule` for the Files tab and `note` for the customer's reply); `outcome` (credibility change per ending id); `summary`. Triggers must be things the customer can see, never hidden truth. |
| Named customer states (v0.9) | A `customerPolicy` rule can give `reply` (a reply id) and optionally `to` (a state in `asset.levels`) and `sends: true` (blocked on frozen days). `events[].if.movedTo` (`state`, `days`) fires on a move; `endings[].if.everAt` matches a state ever reached. |
| Per-target collection (v0.9) | A target can override `cost`, `delay` and `source` per discipline, and set `from` (first day it appears), `closedWhen` (a customer state that closes it) and its own `fallback` text. A burn rule can set `onFirstTasking` (the result arrives, then the source is gone) and `readIn` text. `collection.note` is shown under Files. |
| Names and wording (v0.9) | `customer.short`, `customer.pronouns`, `customer.tipLine`, `adversary`, `endingEyebrow`, `frozenText`. `map` is optional, and so are its parts: a schematic map can use `areas` (extra territories), `zones` (labelled city boxes), `title`, `caption` and `truthNote`, and leave out `river`, `reservoir`, `training`, `friendly` and the scale. `events[].points` and `pointsLabel` add a score line when the event fires. Credibility triggers gain `on: "leave"` with `state` and optional `notTo`. |
| Service record (v1.0) | `record.grades` lists the file-grade changes this scenario causes in later ones (`codeName`, `to`, `reason`); sources are matched across scenarios by code name. A planted report can carry a `callbackTag` (`recycled-photo`, `staged-signals`, `prepared-detail`); the record notes a tag as having got past the player only if they cited that item as evidence, and as caught if they doubted it (#62). `credibility.bonusAt` is the level that earns one extra collection point a day. The order of `crises/index.json` decides what counts as an earlier scenario. |
| `analysts`, `notes` (v1.0) | `analysts`: `id`, `name`, `specialty`, and `reveal` (the trait, shown only in the postmortem). `notes`: `analyst`, `item`, `after` (0 for the day the item arrives, 1 for a day late), `text`, `right` (1, 0.5 or 0) and `why` (the postmortem's one-line verdict). A note on a collection result appears only if the player collected it. Every wrong note must be explainable from items the player had. |
| `board` | Optional. `pinsPerDay` for the hypotheses board (default 3). The board needs no other content: it works from `hypotheses` and the items the player pins. |
